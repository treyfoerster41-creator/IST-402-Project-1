# Local Hotel Storage and Manual Verification - submission draft

I completed the October 1 local-hotel activity in my existing Expedia Lite Vue/FastAPI/SQLite project. I used ZIP `16802` for Scholar Hotel State College and ZIP `02108` for a temporary Boston hotel. The rates and room counts below are simulated classroom data, not Geoapify prices or real availability. My screenshots do not show an API key or `.env` contents.

1. **Schema.** I expected separate storage for provider hotel fields and date-specific simulated values, while keeping the Assignment 1 tables. In DB Browser, I saw `saved_hotels` with the provider ID/key, name, address, latitude, and longitude; `demo_hotel_nights` with hotel/date keys, nightly cents, and rooms available; and the original hotels, trips, users, and bookings tables. The `saved_hotel_zips` association table is present. [Saved-hotel structure](local-hotel-schema-saved-hotels.png) and [nightly structure](local-hotel-schema-nights.png) are my screenshots. A separate database-schema check confirmed defaults of 10000 cents and 20 rooms and that the original rows were not changed.
2. **Add and retain.** I expected Add to create one saved API hotel and five October 10-14 nights, then become disabled. I added The Ritz-Carlton, Boston from ZIP `02108` API results. I saw the success message, disabled Add, Remove button, and five nights at $100.00/20 rooms. When I searched `02108` again, it appeared as the only **Saved locally** result. [After Add](local-hotel-boston-added.png) and [after re-search](local-hotel-boston-saved-result.png) show that change. I also refreshed the browser before re-searching `16802`; Scholar remained saved and its edited values remained visible. The test suite checks repeated saves do not overwrite a changed night.
3. **Remove.** I expected Remove to delete only the temporary saved hotel's local rows. I removed The Ritz-Carlton, Boston, then searched `02108` and saw **API results** again with Add re-enabled. [After Remove](local-hotel-boston-removed.png) shows the interface. A separate SQLite check found no saved Ritz-Carlton row; Scholar and its five nights remained.
4. **Local-first lookup and failure.** I expected a saved ZIP to use only local data, an unsaved ZIP to use the API after an empty local lookup, and a failed local request to show an error. In Firefox's Network panel, [the `16802` search](local-hotel-network-saved-16802.png) showed `saved?zip_code=16802` with HTTP 200 and no nearby request. [The `02108` search](local-hotel-network-fallback-02108.png) showed `saved?zip_code=02108` followed by `nearby?zip_code=02108`, both HTTP 200. During a brief backend outage for this test, [the failure screenshot](local-hotel-backend-error-network.png) showed one failed saved request, no nearby fallback, and a clear saved-hotel lookup error. The backend was restarted afterward.
5. **Edit, save, and reread.** I expected a database edit to appear in the app after I clicked **Write Changes** in DB Browser and repeated the ZIP search. In DB Browser, I changed Scholar Hotel State College's `2026-10-10` row from `10000` cents/20 rooms to `12500` cents/7 rooms. [The edited database row](local-hotel-db-browser-edited.png) shows `12500` and `7` with Write Changes disabled afterward. When I searched `16802` again, [the app showed](local-hotel-16802-edited.png) **$125.00** and **7** for that same date. A separate read of the SQLite file confirmed `12500` and `7` were stored on disk.

My manual observations above are supported by the linked screenshots. Separately, Codex ran 43 backend tests using isolated test databases, the Vue production build, and direct SQLite checks. These automated results do not replace my browser and DB Browser observations.
